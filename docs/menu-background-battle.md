# Menu background battle

The menu demonstration uses `createMenuBattle(seed, config)` in deterministic core code. The default board is 18 by 8 cells: a 14-cell central camera area and two reserved 2-cell deployment strips. Sparse terrain leaves the middle four rows and both strips passable. Every wave has 2–3 units and a frontline infantry/tank; artillery-only waves are excluded. Generation enumerates free strip cells and removes each chosen cell, so it terminates with unique placements without rejection sampling. Invalid configurations are rejected before generation.

Only the dedicated factory adds `menuBattle` policy and `board.menuDeploymentWidth`. Normal map creation and imported player maps do not enable them. The policy stores PRNG state, generation configuration and side wave counters. Unit statistics use the same centralized factory as ordinary maps. IDs include side and wave.

Attacks and counterattacks in demonstration states retain ammunition. Elimination automatically inserts the defeated side's next wave in the shared `applyAction` reducer, emits `menu-reinforced`, and keeps winner null. Surviving units, scores, turn and map remain intact. Pathfinding forbids entry into the opposing deployment strip, which preserves replacement capacity. These restrictions apply through validation and legal action generation. Finite accepted action sequences reproduce identical waves headlessly. No demonstration records enter player replay storage or map formats.

`MenuBattleController` owns two local Heuristic agents and allows one pending decision. Pausing invalidates a pending decision without changing state; disposal also drops current-turn context. Invalid or failed decisions fall back to a legal end-turn. Context is bounded by wave size and movement budget, reset each turn; there is no lifetime log. Run `npm test -- src/ai/menu-battle-controller.test.ts` for the reproducible 600-action seeded soak and finite action replay across waves.

`MenuBackgroundBattleScene` reuses manifest-backed terrain/unit images and `BattleMapRenderer` in ambient mode (no action tints or health overlays). `MenuBattleRunner` feeds accepted routes to `MovementPresenter`, reading saved movement duration at the start of each move. Subsequent moves use new speed settings, including instant movement. Each settled action has a 100 ms pacing interval. Frame delta is capped at 50 ms; no catch-up loop or timer exists. One decision/transition is active at a time. Pause preserves animation progress. Visibility changes freeze the runner; listener and resize subscriptions are removed at scene shutdown.

The camera covers the central 14 by 8 rectangle using the larger horizontal/vertical scale. Within that rectangle, the crop follows the midpoint of the closest opposing pair after accepted transitions so combat at the board edge remains visible on extreme aspect ratios. Its visible world interval never includes either reserved strip, including after wide/tall resize. No input handlers are attached to the background and its input plugin is disabled. Foreground cameras are transparent, supported safe-area dimming and panels use centralized theme opacity. Existing art comes exclusively from the asset manifest; no DOM controls or new artwork are required.

The game coordinator evaluates active foreground membership once per frame. MainMenu (all four views), Language (including authoring/self restart), LM Studio, Host/Join, CampaignLibrary and ReplayLibrary keep one session running. Battle, Result, MapEditor, CampaignEditor and Replay playback hide and suspend it. Return resumes the same controller and presentation. A page reload creates a new random seed/session. Background state never enters foreground return data, user configuration, network inference or saved replay/progress storage. Application destruction removes coordinator and scene listeners.
